# Архитектура MVP CAD/CAE

## Границы ответственности

Текущая структура — хорошая заготовка слоёв, но сама по себе ещё не обеспечивает чистую архитектуру.

| Слой | Ответственность | Замечания по текущему коду |
|---|---|---|
| Models | Общие типы геометрии и сетки | Не зависят от алгоритмов и IO; такое направление зависимостей правильно. Название Models слишком общее: это доменные типы. |
| Geometry | Точная область, контуры, принадлежность точки | Не должна знать о сетке и размере элемента. Отладочная печать в Rectangle нарушает эту границу. |
| Mesh | Узлы, треугольники, граничные рёбра | Не зависит от фигур и mesher, что правильно. Сейчас ID фактически является индексом массива, но это не проверяется. |
| Mesher | Преобразование геометрии в сетку | Зависимость от Geometry и Mesh допустима для сервиса построения сетки. Специализированные mesher подходят для MVP. |
| io | Чтение и запись сетки/результата | Сейчас есть только writers. Импорт должен создавать Mesh без обязательного восстановления CAD-геометрии. |
| HeatProblem / FEMSolver | Физическая постановка и численное решение | Должны работать с Mesh и BoundaryId, независимо от исходной фигуры. |

Models/Mesh2D.h использует локальный Geometry2D.h, а не абстрактный класс фигуры. Это нормальная зависимость типов сетки от координат и меток. Позже Point2D и BoundaryId можно выделить в отдельные маленькие заголовки. Нет необходимости сейчас вводить репозитории, фабрики или отдельный класс на каждый DTO.

## Найденные проблемы

- Mesh::NodeById и ElementById используют непроверенный индекс. AddNode/AddElement не обеспечивают уникальность и непрерывность ID. Для MVP стоит закрепить внутренние ID 0..N-1 и перенумеровывать внешние ID при импорте; затем проверять ссылки, конечность координат, площадь и топологию.
- Rectangle допускает нулевые, отрицательные и неконечные размеры. Тогда контур и треугольники могут стать вырожденными или иметь неправильную ориентацию.
- MesherRectangle.h не имеет include guard. TriangularMesher2D.h — пустая заготовка с определениями нетemplate методов в заголовке, что при нескольких включениях приведёт к ошибкам линковки. Meshe2D.cpp пуст.
- Смешаны соглашения именования, а Git хранит models/... при фактическом каталоге Models/... на macOS. На файловой системе с учётом регистра это может ломать includes. Нужна отдельная нормализация регистра путей.
- Решатель отключён в CMake. Он обращается к старым GetNode/GetEl/GetBoundaryEdge, Node.x/Node.y; HeatProblem вызывает hasBoundaryMarker вместо HasBoundaryMarker. Успешная текущая сборка не означает, что решение теплопроводности работает.
- Robin в FEMSolver — заглушка. Порядок применения разных типов граничных условий влияет на результат: сначала требуется собрать Neumann/Robin, затем наложить Dirichlet. Нужны проверка постановки и диагностика вырожденной системы.
- Dense глобальная матрица и LU ограничивают размер задачи. Для последующего роста понадобится разреженная сборка.
- STLWriter/VTKWriter не реализуют чтение. STL не содержит CAD-кривых и стандартных физических меток; при импорте нужно объединять совпадающие вершины и выделять/назначать границы. Обычный STL поверхности 3D не является готовой 2D-сеткой: MVP должен явно ограничить импорт плоскими треугольниками. VTK также требует явного набора поддерживаемых типов ячеек и данных меток.

## Представление кривой — первый реализованный шаг

Contour2D содержит упорядоченные BoundaryCurve2D. У каждой есть Curve2D (std::variant отрезка и круговой дуги) и BoundaryId. pointAt(t), t в [0,1], даёт точку точной геометрии. CircularArc2D хранит центр, радиус, начальный угол и подписанный угловой размах в радианах. Полный круг — размах 2*pi. Внешняя граница обходится против часовой стрелки, отверстие — по часовой.

Это намеренное изменение API: segments заменён на curves, BoundaryId перенесён из LineSegment2D в BoundaryCurve2D. Rectangle уже адаптирован. Контур пока остаётся простой структурой: замыкание, допустимость произвольной дуги и согласованность isHole с направлением не валидируются автоматически.

std::variant подходит для небольшого набора стандартных кривых: данные копируются по значению, нет владения указателями. При появлении сплайнов можно добавить новый тип и расширить вычисление параметризации. Абстрактный интерфейс Curve уместен позже, если понадобится подключать неизвестные заранее типы кривых.

Circle хранит радиус и центр, проверяет параметры и выдаёт одну полную дугу. Геометрия не хранит число сегментов. MesherCircle строит центр и концентрические слои, затем линейные треугольники и граничные хорды с исходной меткой. У него N угловых сегментов и L радиальных слоёв: 1+N*L узлов, N*(2*L-1) треугольников, N граничных рёбер.

Граничные узлы лежат на окружности, но область линейной сетки — вписанный многоугольник. Радиальное разбиение не гарантирует качество: около центра возможны узкие треугольники. Увеличение числа радиальных слоёв не улучшает аппроксимацию окружности; для этого нужно увеличивать N.

Пример использования с существующим экспортом:

```cpp
#include "Geometry/Circle.h"
#include "Mesher/MesherCircle.h"
#include "io/VTKWriter.h"

Circle circle(2.0, Point2D{3.0, -4.0}, 17);
Mesh mesh = MesherCircle(64, 8).generateMesh(circle);
VTKWriter::Write(mesh, "circle.vtk");
```

## Следующие шаги

1. Закрепить и проверять инварианты Mesh, согласовать регистр путей, восстановить сборку и тест простейшей тепловой задачи.
2. Добавить кольцо: внешняя дуга CCW, внутренняя CW, две разные метки. Для него требуется отдельная триангуляция без центрального узла.
3. Вынести дискретизацию произвольного контура в mesher: по максимальному шагу и погрешности хорды; сохранить метки и точки стыка кривых.
4. Для смешанных контуров и отверстий добавить constrained triangulation с управлением качеством. Не привязывать общий алгоритм к dynamic_cast конкретных фигур; он должен принимать контуры/полигональные ограничения.
5. Добавить адаптеры импорта и явный контракт поддерживаемых STL/VTK. Физические постановки теплопроводности, электростатики и гидродинамики держать отдельно: первые две могут использовать общий скалярный оператор, гидродинамике нужны собственные неизвестные и дискретизация.

Общий виртуальный mesher пока не введён: специализированные generateMesh имеют разные параметры. Его контракт имеет смысл зафиксировать вместе с общей дискретизацией и требованиями к качеству.

## Проверки

CTest проверяет точную параметризацию круга, некорректные параметры, несколько разрешений сетки, положительные площади, площадь вписанного многоугольника, топологию рёбер, отсутствие внутренних разрывов, метки и радиусы граничных узлов. Прямоугольник проверяется на неравномерных количествах узлов по осям.
